## 5. CI build fix (2026-11-08)

The first push failed in Cloudflare's build (`npx wrangler deploy`, wrangler
4.x): the config was Pages-shaped (`pages_build_output_dir`), and `wrangler
deploy` cannot deploy a Pages project ("Could not detect a directory
containing static files"). Reproduced locally with `wrangler@4.158.0`; fixed
by making the root `wrangler.toml` a Workers-with-static-assets project:

- `wrangler.toml`: `main = "worker/src/app.js"` + `[assets] directory="./app"`
  (`run_worker_first = true`, `not_found_handling = "404-page"`) +
  `[[durable_objects]] WAREHOUSE_LEDGER → WarehouseLedger` + `[[migrations]]`
  (replacing the Pages-era `[[services]]` placeholder).
- `worker/src/api-router.js` (new): dispatches `/api/*` to the **exact**
  `functions/api/**` modules (method + path table, `:id` params, the same
  `_middleware.js` first) — no copied handler code.
- `worker/src/app.js` (new): one entry exporting fetch (API + `env.ASSETS`
  fallback), `queue()` and `scheduled()` and the `WarehouseLedger` class.
- Verified: `npx wrangler deploy --dry-run` bundles clean (139.22 KiB);
  live `npx wrangler dev` smoke — health/login/stock/movement through the
  real Durable Object stub, 403+Blocked audit on cross-keeper write, 404
  bounce page; `bash tools/check.sh` → `CHECK: all green` (58 + lint).

Follow-up after the first real CI deploy (same day): the build reached the
Cloudflare API and was rejected with `KV namespace 'PLACEHOLDER' is not valid
[code: 10042]` — **the API validates binding IDs at upload**, so placeholder
IDs can never ship (a `--dry-run` cannot catch this; it never reaches the
API). Also warned: Worker name mismatch (config `fabric-roll-stock` vs CI
project `inventoryazhartexcloudflare`; the CI overrides and offers to open a
PR). Fix: `wrangler.toml` now deploys with only self-contained bindings
(`ASSETS` + `WarehouseLedger` + migrations) and carries every resource
binding as a commented template (create → paste real ID → uncomment → push);
`name = "inventoryazhartexcloudflare"` matches the CI. Verified by the
CI-faithful check (`git archive` checkout without `node_modules`, bare `npx
wrangler deploy --dry-run`): 11 assets, 139.22 KiB, only the two bindings.

Test-devDependency note: `better-sqlite3` is pinned to `12.11.1` (tests only —
`tests/_local-d1.js`). v13.x releases no longer attach prebuilt binaries, and
this sandbox blocks both `nodejs.org` (node-gyp headers) and the GitHub
release-asset hosts (`objects/​release-assets.githubusercontent.com`); 12.11.1
ships prebuilts for the node 22 and 24 ABIs and exposes the identical API the
adapter uses (verified: 59/59 tests green on 12.11.1). The Cloudflare build
(`npm clean-install`) installs it normally.

Second follow-up (same day, third deploy attempt): with bindings trimmed the
upload reached the DO migration and the free-plan API rejected `new_classes`
with `In order to use Durable Objects with a free plan, you must create a
namespace using a new_sqlite_classes migration [code: 10097]`. Fix: both
wrangler.toml files now declare `new_sqlite_classes = ["WarehouseLedger"]`
(the classic storage API the class uses works unchanged on the SQLite
backend). After this, the same build log shows the deploy proceeding past
bindings (only `WAREHOUSE_LEDGER` + `ASSETS`) with the name-mismatch warning
gone.

Third follow-up (same day, support round): first-run logins all reported
"Wrong username or password" — the login UI mapped EVERY failure to that one
toast, hiding the real cause (unbound D1, missing schema, or unseeded users).
Fix: `login.js` now distinguishes `CONFIG` (no `env.DB`), `NO_SCHEMA` and
`NO_ACCOUNTS` (503 each, each carrying the exact remediation command) from
genuine `BAD_CREDENTIALS` (401), `auditLogin` never throws when the database
itself is broken, and the login toast maps error codes to dedicated EN/AR
i18n keys (`login.config`, `login.noAccounts`). Covered by
`tests/api.test.js` ("login setup diagnostics").

Fourth follow-up (same day, "fix automatically"): the live app correctly
reported `CONFIG` (D1 not bound), but binding resources still required manual
dashboard work. Added `tools/provision.mjs` (npm `postinstall`, so the
Cloudflare build's `npm clean-install` runs it before `npx wrangler deploy`):
it finds-or-creates D1 `fabric-roll-stock` / KV `CACHE` / R2
`fabric-roll-exports` / the six queues using the build's `CLOUDFLARE_API_TOKEN`,
rewrites the scissors-marker region of `wrangler.toml` with real IDs (build
workspace only — IDs never committed), and applies `migrations/` idempotently.
Degrades per-resource on permission errors (the login toast names whatever is
still missing). Verified: `--self-test` in `tools/check.sh` (rewrite logic,
offline) and a simulated provisioned config passing `wrangler deploy
--dry-run` with all six bindings. Without a token the script skips cleanly.

Fifth follow-up (same day, "one-tap setup"): the binding landed but the seed
had not — pasting 500 KB of SQL into the D1 console from a phone is not
happening. The app can now initialize its own database: `POST
/api/auth/setup` (open path, rate-limited, audited) runs ONLY while zero
accounts exist (409 `ALREADY_SET_UP` forever after), wipes partial data
(runtime-discovered tables, FK-tolerant passes), and applies the exact
`migrations/0001–0003` content embedded as `shared/seed-sql.js` (generated by
`tools/make_seed_module.py`, single-sourced from the SQL). The login screen
shows a one-tap **Initialize database & load demo data** button when the API
reports `NO_ACCOUNTS`/`NO_SCHEMA`, then retries the typed credentials
automatically. Bundle cost: +540 KB raw / +39 KB gzip (Total Upload 679.58
KiB / gzip 70.82 KiB). Covered by `tests/api.test.js` ("first-run setup",
partial-state + schema-missing scenarios): 59 tests green.

Sixth follow-up (2026-11-09, "still same error"): PR #6 was merged but the
live app kept the old behaviour, so the deploy pipeline itself became the
suspect. Five failure modes hardened in one sweep: (1) `tools/provision.mjs`
can no longer fail a build — its entry is wrapped and exits 0 in every case
except `--self-test`; (2) `better-sqlite3` moved to `optionalDependencies`
so a native-build failure in the build image can never kill `npm ci`;
(3) `app/_headers` now sends `Cache-Control: no-cache` for all assets (the
`app.js` reference had no cache-busting); (4) the login screen probes
`GET /api/auth/setup` on render and shows the one-tap Initialize button
immediately — no failed login needed first; (5) `offerSetup` scrolls the
button into view. `GET /api/auth/setup` doubles as the one-URL
"is the new build live?" check. Tests: 60 green.

Seventh follow-up (2026-11-09, "add users and fix, don't stop"): the blank
phone screenshots were not a missing button — the page itself is panned/shifted
away from the login card after the Android virtual keyboard closes, a
Chrome/WebView 76+ viewport bug hitting `100vh` + `vh`-based margins (research:
enzoblain/Palabre#67 is the identical bug with the identical fix recipe;
ionic-framework#19065 documents the keyboard-resize break). Fixes:
`min-height: 100dvh` (vh fallback kept) on `#shell`; `.login-wrap` margins
switched from `7vh` to rem; `.login-demo` tables get `overflow-x: auto`
(the horizontal scrollbar in the screenshots); `safeTop()` scroll reset on
`pageshow` / `visibilitychange` / `visualViewport resize` / `focusout`
(login screen only). "Add users" honoured literally: the login screen now
**auto-runs the first-run setup** when the probe reports zero accounts
(button kept as fallback), and `GET /api/auth/setup?go=1` is a one-tap
bootstrap link that works from any browser regardless of any cached SPA.
Tests: 62 green (new: api bootstrap-link test, ui auto-seed test).
