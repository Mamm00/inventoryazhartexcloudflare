# DEPLOY.md — deploying Fabric Roll Stock to Cloudflare

This repo deploys with the exact command your Cloudflare build runs —
**`npx wrangler deploy` from the repository root** (wrangler 4.x). The root
`wrangler.toml` is a complete **Workers-with-static-assets** project: the SPA
from `app/`, the API (the same `functions/api/**` modules), the
`WarehouseLedger` Durable Object, queue consumers and cron triggers — one
deploy serves everything. Do not deploy manually from a laptop — the
deliverable is a green PR that Cloudflare builds from `main`.

## 0. What the deploy runs

| Piece | Where it lives |
| --- | --- |
| Static SPA (`index.html`, `app.js`, `styles.css`, `logo.svg`, `404.html`, `landing.html`) | `app/` — the `[assets]` directory |
| API (`/api/*`, RBAC middleware) | `functions/api/**`, dispatched by `worker/src/api-router.js` |
| Worker entry (fetch + queue + scheduled + DO export) | `worker/src/app.js` |
| D1 schema + generated seed | `migrations/` (`0002_seed.sql` is generated — never hand-edit) |
| Optional standalone companion (split topology) | `worker/wrangler.toml` + `worker/src/index.js` — leave undeployed unless you split |

`npx wrangler deploy` bundles `worker/src/app.js` (it imports the exact Pages
Function modules from `functions/api/**` — no copied code), uploads `app/` as
static assets, and declares the `WarehouseLedger` Durable Object via
`[[durable_objects]]` + `[[migrations]]`. Verified in CI-equivalent conditions
with `npx wrangler deploy --dry-run` (`tools/check.sh` stage 5 runs it).

## 1. Create the D1 database and apply migrations

```bash
wrangler d1 create fabric-roll-stock
# uncomment the [[d1_databases]] block in wrangler.toml, paste the database_id
wrangler d1 migrations apply fabric-roll-stock --remote
```

Migrations run in order: `0001_schema.sql`, `0002_seed.sql` (generated by
`tools/make_seed_sql.py`; re-run `npm run build` if you change the plan
tables), `0003_indexes.sql`.

## 2. Connect the repository in the Cloudflare dashboard

Cloudflare Dashboard → Workers & Pages → Create → **Workers** → Connect to Git
→ select this repository. Build settings:

| Setting | Value |
| --- | --- |
| Production branch | `main` |
| Build command | leave empty (nothing to build; `wrangler` bundles) |
| Deploy command | `npx wrangler deploy` (the default) |
| Root directory | `/` (repo root) |

The first deploy needs **no pre-created resources**: `wrangler.toml` binds only
`ASSETS` and the `WarehouseLedger` Durable Object (self-contained). Every
resource binding ships as a **commented template block** — the Cloudflare API
rejects placeholder IDs at upload (real-world error: `KV namespace
'PLACEHOLDER' is not valid [code: 10042]`), so create the resource, paste its
real ID into the template, uncomment the block, and push. The Worker deploys
under the name `inventoryazhartexcloudflare` (the CI project name — keep
`name` in `wrangler.toml` in sync, or the build warns and overrides). The
Durable Object migration uses `new_sqlite_classes` — required for Durable
Objects on the **free plan** (API error 10097 for `new_classes`); the class
code is identical on both storage backends.

### Automatic provisioning (default)

The build also runs **`tools/provision.mjs`** (wired as npm `postinstall`,
which `npm clean-install` executes before `npx wrangler deploy`). When the
build environment carries a `CLOUDFLARE_API_TOKEN` — it does, so wrangler can
deploy — the script finds-or-creates the D1 database `fabric-roll-stock`, the
KV namespace `CACHE`, the R2 bucket `fabric-roll-exports` and the app queues,
writes their real IDs into the scissors-marker region of `wrangler.toml`
(build workspace only — account IDs are never committed), and applies
`migrations/` (idempotent — tracked in `d1_migrations`, skipped when a
hand-seeded `users` table is detected). Every step degrades gracefully on
permission errors: that resource stays a commented template and the login
toast names the exact missing step. Check any build log for `provision:`
lines. The manual path in §5 remains the fallback.

> **Classic Pages project instead?** Create a *Pages* project with **build
> output directory `app`** from the same repo — Pages auto-mounts
> `functions/api/**` and serves `app/` exactly as before. The Durable Object
> is not available on Pages: `movements` then uses the identical ledger
> implementation inside the Worker (`shared/ledger-core.js` — same
> negative-stock guarantee, no per-key serialisation). The Workers deploy
> above is the recommended path.

## 4. Bindings (Settings → Bindings)

`wrangler.toml` commits the non-secret binding *shape* so the configuration is
versioned with the code; the dashboard entries attach the real resource IDs.
`worker/wrangler.toml` is only for the optional split companion worker
(`worker/README`).

| Binding | Type | Configured in | Notes |
| --- | --- | --- | --- |
| `DB` | D1 | uncomment `[[d1_databases]]` + real ID | `fabric-roll-stock` |
| `CACHE` | KV | uncomment `[[kv_namespaces]]` + real ID | rate limits, idempotency, digests |
| `EXPORTS` | R2 | wrangler.toml | backups, CSV/PDF exports |
| `AUDIT_QUEUE` | Queue producer | wrangler.toml | consumed by the worker's `queue` handler |
| `ANALYTICS` | Analytics Engine | wrangler.toml | login attempts, stock mutations |
| `WAREHOUSE_LEDGER` | Durable Object | wrangler.toml (`[[durable_objects]]` + `[[migrations]]`) | auto-bound by the deploy; on classic Pages bind the companion worker's service instead |
| Workers AI | AI | dashboard only | assistive features, never stock numbers |
| Vectorize | Vectorize | dashboard only | semantic colour search |
| Images | Images | dashboard only | swatch/fabric photos |
| Browser Rendering | Browser Rendering | dashboard only (companion worker) | server-side PDF letterhead |
| Turnstile | Turnstile widget | dashboard + `TURNSTILE_SECRET` | login + sensitive mutations |
| Cloudflare Access | Access | dashboard + `ACCESS_CLIENT_SECRET` | `Cf-Access-Jwt-Assertion` in middleware |

## 5. First deploy sequence (checklist)

```bash
wrangler d1 create fabric-roll-stock            # 1. database
# 2. uncomment [[d1_databases]] in wrangler.toml, paste the database_id
wrangler d1 migrations apply fabric-roll-stock --remote
git push origin main                            # 3. the build runs `npx wrangler deploy`
```

Then, resource by resource: create it, uncomment its template block with the
real ID, push (each push redeploys). Enable Turnstile on the login form (the
SPA posts `turnstileToken`),

> **No CLI at hand?** Once the `DB` binding exists, the app finishes the setup
> itself: log in and the screen offers **"Initialize database & load demo
> data"** (Arabic: تهيئة قاعدة البيانات) whenever the database has zero
> accounts. One tap wipes any partial data and applies `migrations/0001–0003`
> (the same SQL, embedded in the worker) — and the endpoint refuses to ever
> run again once an account exists. The login screen even **auto-runs** this
> setup on load when the database is empty — or tap the one-tap bootstrap
> link from any browser: `https://<your-host>/api/auth/setup?go=1` (same
> guards: refuses once any account exists, rate-limited, audited). To confirm
> the new build is serving:
> open `/api/auth/setup` in the browser — JSON `{"needed":true}` means it is
> live (a 404 means an older build is still deployed).
and add an Access application in front of the site if SSO is desired (the
middleware validates `Cf-Access-Jwt-Assertion` when `ACCESS_CLIENT_SECRET` is
set).

## 7. Local development

```bash
npm run build
wrangler d1 execute fabric-roll-stock --local --file migrations/0001_schema.sql
wrangler d1 execute fabric-roll-stock --local --file migrations/0002_seed.sql
wrangler d1 execute fabric-roll-stock --local --file migrations/0003_indexes.sql
npx wrangler dev --port 8788 --ip 0.0.0.0       # the CI's exact deploy shape on Miniflare
```

`npx wrangler dev` serves the whole stack (assets + API + Durable Object +
queues + cron) from the same `wrangler.toml` the deploy uses. The tests do not
need the server: `npm test` runs all four suites in-process against a local D1
(`tests/_local-d1.js`) plus the real `WarehouseLedger` class.

## 8. Why the API lives in `functions/api/**`

The handler modules are genuine Pages Functions (they can be mounted by a
classic Pages project with zero changes) *and* are imported by
`worker/src/api-router.js` for the single-Worker deploy. One source of truth;
`guard()`/RBAC runs server-side in both shapes.
