# DEPLOY.md — deploying Fabric Roll Stock to Cloudflare Pages

This repo is built for **Cloudflare Pages' Git integration**: every push to
`main` builds and deploys; pull requests get preview deployments. Do not deploy
manually from a laptop — the deliverable is a green PR that Pages builds.

## 0. What Pages will run

| Piece | Where it lives |
| --- | --- |
| Static SPA (`index.html`, `app.js`, `styles.css`, `logo.svg`, `404.html`, `landing.html`) | `app/` — the Pages build output |
| Pages Functions (`/api/*`, RBAC middleware) | `functions/` |
| D1 schema + generated seed | `migrations/` (`0002_seed.sql` is generated — never hand-edit) |
| Companion Worker (Durable Objects, queues, cron) | `worker/` |

## 1. Create the D1 database and apply migrations

```bash
wrangler d1 create fabric-roll-stock
# paste the returned database_id into wrangler.toml (both [[d1_databases]] blocks)
wrangler d1 migrations apply fabric-roll-stock --remote
```

Migrations run in order: `0001_schema.sql`, `0002_seed.sql` (generated by
`tools/make_seed_sql.py`; re-run `npm run build` if you change the plan
tables), `0003_indexes.sql`.

## 2. Deploy the companion Worker FIRST

The Pages project binds the Worker's `WAREHOUSE_LEDGER` namespace (the
`WarehouseLedger` Durable Object serialises stock mutations per warehouse and
refuses negative stock). Pages Functions can *produce* to Queues but cannot
*consume* them — the Worker is also the queue consumer and cron runner.

```bash
cd worker
wrangler deploy
cd ..
```

`worker/wrangler.toml` declares the DO class, the three queue consumers with
dead-letter queues, and the cron triggers (15-min session cleanup, daily
low-stock digest 06:00 Africa/Cairo, daily 02:00 integrity check, weekly Sunday
R2 backup with sha256 manifest).

## 3. Connect the repository in the Cloudflare dashboard

Cloudflare Dashboard → Workers & Pages → Create → Pages → Connect to Git →
select this repository. Build settings:

| Setting | Value |
| --- | --- |
| Production branch | `main` |
| Build command | `npm run build` |
| Build output directory | `app` |
| Root directory | `/` (repo root) |

`npm run build` runs `tools/make_seed_sql.py`, `tools/make_landing.py` and
`tools/copy_shared.py` — all deterministic, so a build never dirties the repo.

## 4. Environment variables (Production **and** Preview)

| Variable | Value |
| --- | --- |
| `NODE_VERSION` | `20` |
| `CLOUDFLARE_ACCOUNT_ID` | optional, for tooling |
| `D1_DATABASE_ID` / `KV_NAMESPACE_ID` | optional, only if the builder needs them |
| `TURNSTILE_SECRET` | Turnstile secret key (login protection) |
| `ACCESS_CLIENT_SECRET` | Access JWT shared secret (if SSO is enabled) |
| `EXPORT_TOKEN` | token protecting `/api/export/offline` |

## 5. Bindings (Settings → Bindings, both environments)

`wrangler.toml` commits the non-secret binding *shape* so the configuration is
versioned with the code; the dashboard entries attach the real resource IDs.

| Binding | Type | Configured in | Notes |
| --- | --- | --- | --- |
| `DB` | D1 | wrangler.toml + dashboard ID | `fabric-roll-stock` |
| `CACHE` | KV | wrangler.toml + dashboard ID | rate limits, idempotency, digests |
| `EXPORTS` | R2 | wrangler.toml | backups, CSV/PDF exports |
| `AUDIT_QUEUE` | Queue producer | wrangler.toml | consumed by the companion Worker |
| `ANALYTICS` | Analytics Engine | wrangler.toml | login attempts, stock mutations |
| `WAREHOUSE_LEDGER` | Service binding | dashboard (after Worker deploy) | → `fabric-roll-ledger-worker` |
| Workers AI | AI | dashboard only | assistive features, never stock numbers |
| Vectorize | Vectorize | dashboard only | semantic colour search |
| Images | Images | dashboard only | swatch/fabric photos |
| Browser Rendering | Browser Rendering | dashboard only | server-side PDF letterhead |
| Turnstile | Turnstile widget | dashboard + `TURNSTILE_SECRET` | login + sensitive mutations |
| Cloudflare Access | Access | dashboard + `ACCESS_CLIENT_SECRET` | `Cf-Access-Jwt-Assertion` in middleware |

## 6. First deploy sequence (checklist)

```bash
wrangler d1 create fabric-roll-stock            # 1. database
wrangler d1 migrations apply fabric-roll-stock --remote
cd worker && wrangler deploy && cd ..           # 2. DO + queues + cron
git push origin main                            # 3. Pages builds from main
```

Then in the dashboard: attach `WAREHOUSE_LEDGER`, enable Turnstile on the login
form (the SPA posts `turnstileToken`), and add an Access application in front of
the site if SSO is desired (the middleware validates
`Cf-Access-Jwt-Assertion` when `ACCESS_CLIENT_SECRET` is set).

## 7. Verification after merge

- `https://<project>.pages.dev/api/health` returns `200 {"ok":true,...}`
- `https://<project>.pages.dev/` serves the SPA; `/#/inventory` deep-links to Inventory
- An unknown path bounces through `404.html` back to a hash route
- Sign in with `keeper1` / `mostafa123` → Stock Overview shows exactly 5 shed cards

## 8. Local development

```bash
npm run build
wrangler d1 execute fabric-roll-stock --local --file migrations/0001_schema.sql
wrangler d1 execute fabric-roll-stock --local --file migrations/0002_seed.sql
wrangler d1 execute fabric-roll-stock --local --file migrations/0003_indexes.sql
npx wrangler pages dev --port 8788 --ip 0.0.0.0   # full stack on Miniflare
python3 tools/serve.py                            # read-only preview without wrangler
```

If the companion Worker is not running locally, the Pages Functions fall back
to the identical shared mutation implementation (`shared/ledger-core.js`) —
the Durable Object is authoritative in production.

## 9. Honesty notes

- The writable app **requires Cloudflare and HTTPS**; the offline snapshot
  (`/api/export/offline`) is **read-only**.
- Server-side RBAC (`shared/permissions.js`) is enforced in every Pages Function
  and in the Durable Object. The browser copy of `can()` only hides buttons.
- Workers AI features are **assistive** — they never author stock numbers.
